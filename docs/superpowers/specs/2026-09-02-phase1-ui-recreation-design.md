# imgsorter-app — Phase 1 Design: TanStack Start UI Recreation

**Date:** 2026-09-02
**Status:** Approved design (spec pending user review)
**Scope:** Phase 1 only — recreate the imgsorter-ui-v1 prototype UI in TanStack Start, modularized and URL-routed, backed by mock data. No backend/engine wiring.

## 1. Context & source material

This project combines three existing repositories:

1. **imgsorter-v2** — a Node/TypeScript engine for indexing local files and detecting
   duplicates across directories. `Runner` orchestrates phases (`scan`, `resync`,
   `records`), `DbService` uses better-sqlite3 (`entries` + `records` tables),
   `FileService` does edge hashing, and a `ProgressEmitter` emits typed progress
   events. `RunConfiguration` is zod-validated. It is structured to be used
   programmatically. **Deferred to Phase 2+** (per decision).
2. **imgsorter-ui-v1** — a design/UX prototype. Everything lives in one ~34KB
   `App.tsx` (mock data, all pages, all state, all styling) plus `styles.css`.
   React 19 + Vite + Mantine v9 + lucide-react, dark cyan theme, no router,
   no backend. Its `HANDOVER.md` is the authoritative UX contract.
3. **basic-typescript-template** — the user's tooling defaults (pnpm, TS7 strict,
   oxlint, Vitest, Prettier, Lefthook, esbuild).

**Decisions made during brainstorming:**

- **Engine integration:** copy/vendor imgsorter-v2 source into this repo's server
  side, **deferred entirely to Phase 2**. Phase 1 contains no engine code.
- **Persistence (Phase 2+):** recommended default is a SQLite `app_config` table
  managed by the engine (single source of truth). Confirmed as default; not
  implemented in Phase 1.
- **State management:** no TanStack Store. Local `useState` + TanStack Router
  search params for cross-page filters + one small React context for drawer and
  scan state. Revisit store/`useSyncExternalStore` in Phase 2 for the scan stream.
- **Dead code:** drop the unused `FilePreview` component and the dead grid/list
  layout branches in `Files`. Keep only the table layout actually used.

## 2. Goals

- Recreate the polished v0 UI exactly (visual fidelity) in a maintainable,
  modularized structure.
- Replace the single `App.tsx` with feature folders and thin URL-backed routes.
- Introduce real URLs (`/`, `/duplicates`, `/unique-files`, `/analytics`,
  `/browse`, `/activity`, `/preferences`) so views/tabs are addressable.
- Set up the project with the user's template tooling conventions.
- Keep all data as in-memory mock data (parity with prototype). No backend calls.

## 3. Non-goals (Phase 1)

- No engine code, no `server/` directory, no `better-sqlite3`.
- No real filesystem scanning, hashing, or persistence.
- No delete/move/keeper actions, no Reveal/Open-file handlers.
- No SSR-specific data loading (routes render static mock data).
- No comprehensive test suite — only a few smoke tests.

## 4. Technology stack

- TanStack Start (Vite-based, React 19, TypeScript 7 strict)
- Mantine v9 core + `@mantine/hooks`
- lucide-react
- Existing `styles.css` + custom theme tokens (dark cyan `#18c7d8`, `#101318` bg, etc.)
- Tailwind installed but unused (matches prototype)
- Tooling: pnpm, oxlint, Vitest, Prettier, Lefthook (from basic-typescript-template)

**Organization principles:**

- `app/components/common/` — components reused across 2+ features or by the app
  shell (Sidebar, AppHeader, AppFooter, FilePreviewDrawer, FilterBar,
  PaginationControls, DirectoryTree).
- `app/features/<name>/` — route/page components plus components used by exactly
  one feature (MetricCard, StorageMap, DuplicateGroupTable, DirectoryPicker,
  KeepToggle, etc.).
- `app/routes/` — thin route files that mount the matching feature page; no
  business logic.
- `app/lib/` — shared types, formatters, mock data.

## 6. Data model (mock, for Phase 1)

Mirror the prototype's types exactly so the Phase 2 swap to the engine's real
`FileEntry`/`FileRecord` is low-friction. (Birthtime canonical type decided as a
string for Phase 1 parity; revisit when wiring the engine which uses `Date`.)

```ts
type Entry = {
  id: number;
  size: number;                 // bytes
  directory: string;            // e.g. 'C:/Media/2025'
  extension: string;            // '.jpg' | '.png'
  filename: string;
  birthtime: string;            // ISO-ish string (parity with prototype)
  hash: string | null;          // null = not a duplicate in demo data
  path: string;
};

type DirectoryNode = {
  label: string;                // e.g. 'Media (C:)'
  path: string;                 // e.g. 'C:/Media'
  children?: DirectoryNode[];
};

type DuplicateGroup = {
  hash: string;
  name: string;                 // representative filename
  count: number;
  space: string;                // pre-formatted, e.g. '112.8 MB'
  files: Entry[];
};
```

`mock-data.ts` holds `entries` (18 items), `groups` (3), `directoryTree` (3
roots), `thumbs` (6 Unsplash URLs), initial `logs` (3 entries), and the various
hardcoded Overview/Analytics/Preferences arrays. `format.ts` holds the byte
formatter.

## 7. App shell & cross-page state

- `__root.tsx` renders the shell: `Sidebar` + `AppHeader` + `<Outlet />` +
  `AppFooter` + the shared `FilePreviewDrawer`.
- **Sidebar** renders brand, the global **Scan library** button (sets
  `scanActive`, navigates to `/activity`, prepends a "Scan started" log), the
  scan-state block, the main nav (6 items, Duplicates shows an orange `3` badge),
  and the Preferences entry pinned at the bottom.
- **AppHeader** holds the mobile title, global search `TextInput`, directory
  `Select`, extension `Select`, status dot, and export button.
- **AppFooter** shows file/size totals and last-scan line.

**Cross-page state:**

- Global filters (`query`, `dir`, `ext`) → TanStack Router search params on the
  filter-consuming routes **only** — `/unique-files`, `/browse`, and
  `/duplicates` — so they are URL-addressable and shareable. The AppHeader still
  shows the filters on every page, but non-filterable routes (Overview,
  Analytics, Activity, Preferences) do not carry these params. Browse adds a
  route-scoped `selectedDirs` search param for its multi-folder `DirectoryTree`
  filter (configured from Browse only, not shared cross-page).
- `selectedFile` (drawer), `scanActive`, `logs`, `keepers` → a single lightweight
  client context (`AppProvider` / `useApp`). Low-frequency, few consumers — no
  store needed.

The `filtered` memo (global search + dir + ext pipeline) is recomputed in the
context/provider and consumed by the Files and Duplicates features. Browse
composes the same global `filtered` pipeline with its route-scoped
`selectedDirs` selection.

## 8. Features summary (behavior contract from HANDOVER)

- **Overview:** metric grid (6 cards), storage map, last-run steps + warning,
  "At a glance" largest files (links to Analytics).
- **Duplicates:** duplicate groups by hash; per-group expand/collapse; search;
  directory multi-select popover picker; extension/count/size filters; sortable
  columns; keeper selection state (no consequence yet); clicking a file opens the
  drawer. The `KeepToggle` (per-row checkbox/badge marking which copy to keep)
  renders **only** within Duplicates — on each duplicate group's rows and the
  drawer opened from them. `keepers` state lives in the global context so the
  selection persists across navigation; it is not surfaced on Files/Browse.
- **Files (Unique Files + Browse):** filterable table (filename/path search,
  directory, count, size, extension). Unique Files adds an Actions column with
  "Needs backup" badge. Browse adds the `DirectoryTree` multi-folder sidebar
  filter, scoped to the Browse route via the `selectedDirs` search param. Clicking a row opens the drawer.
- **Analytics:** "Ranked by size" and "Ranked by copies" tables with independent
  page-size Selects and Previous/Next pagination.
- **Activity:** "Current scan" card (progress + status branching on `scanActive`)
  and a reverse-chronological event log with status badges (Warning/Running/
  Complete). No timer drives progress in Phase 1.
- **Preferences:** two tabs (Application configuration, Directories) with all the
  fields/switches/add-remove flows from the prototype, in-memory only. Tabs can be
  toggled; visibility is state-driven (recommend conditional render over the
  prototype's CSS-hiding, since we are not preserving the single-file constraint).

## 9. Error handling

Phase 1 has no data-loading or network errors to handle. Local form validation in
Preferences (empty/duplicate path messages) is preserved. No backend error paths.

## 10. Testing & verification

- `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` must pass.
- Visual verification: render the app and compare each view + drawer against the
  imgsorter-ui-v1 build to confirm parity (via screenshots).
